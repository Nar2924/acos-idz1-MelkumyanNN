## 1. Задача

На клумбе растут цветы. У каждого цветка есть начальная влажность и скорость высыхания, которая выбирается случайно из заданного диапазона. Когда влажность падает до порога увядания, цветок можно полить. При достижении порога засыхания он погибает.

Два садовника работают одновременно. Каждый выбирает самый сухой из доступных цветов и за один раз поливает только один цветок. Одному цветку назначается только один садовник. После полива действует интервал защиты. Повторный полив в этот интервал приводит к переливу и гибели цветка. Симуляция заканчивается по истечении заданного времени, при гибели всех цветов или по сигналу остановки.

## 2. Реализация

| Программа | Назначение |
|---|---|
| `garden_app` | Сервер. Хранит состояние клумбы, обновляет его по таймеру, принимает запросы садовников и публикует события. |
| `gardener_app` | Клиент-садовник. Сообщает серверу свой номер и скорость полива, выбирает цветок из предложенных и ждёт окончания работы. |
| `monitor_app` | Клиент-наблюдатель. Показывает состояние клумбы на момент подключения, события и итоговую статистику. |

Модель клумбы находится в `garden/garden.c`. На каждом шаге влажность свободного цветка уменьшается на произведение скорости высыхания и длительности шага. При поливе влажность увеличивается с заданной скоростью, пока садовник не внесёт всю порцию воды. После этого сервер освобождает садовника и отмечает время окончания защиты. Погибшие цветы остаются в итоговой статистике.

Подключения построены по схеме из презентации «Семинар 09. Сетевые взаимодействия. Протокол TCP» (слайды 8 и 13–17). Сервер создаёт сокет IPv4/TCP, выполняет `bind()` и `listen()`. При вызове `accept()` он получает отдельный дескриптор для каждого клиента. Садовник и наблюдатель создают сокет и вызывают `connect()` с адресом и портом сервера. Команды разделяются символом новой строки. Сервер собирает команду из полученных байтов и сохраняет остаток сообщения при частичной записи.

Серверный цикл в `garden/server.c` обслуживает неблокирующие сокеты через `poll()` и следит за временем очередного шага. Садовник отправляет `READY`, когда готов к поливу. Если подходящих цветов пока нет, сервер сохраняет его готовность и проверяет доступность цветов после следующих шагов. Когда появляется доступный цветок, сервер отправляет список вариантов, а садовник отвечает командой `SELECT <flower> <cycles>`.

В поле `cycles` садовник указывает число завершённых поливов, которое видел при выборе. Сервер проверяет, свободен ли цветок и совпадает ли это число с текущим. При конфликте он отвечает `RETRY`. Запрос с актуальным числом поливов во время защиты даёт `OVERWATER`. Обычный список вариантов содержит только увядающие цветы, свободные и вышедшие из защиты. Проверка и назначение выполняются в одном серверном цикле, поэтому два садовника не могут одновременно занять один цветок.

Наблюдатель отправляет `MONITOR` и сразу получает `SNAPSHOT` с состоянием цветов и садовников. Далее сервер присылает новые события. После переподключения наблюдатель получает новый снимок. Очередь отправки ведётся отдельно для каждого клиента и ограничена 256 КиБ. Если она переполняется, сервер закрывает это соединение, а другие клиенты продолжают получать данные.

Если садовник отключается во время полива, сервер освобождает цветок и сохраняет уже внесённую воду. При остановке сервер отправляет итоговое сообщение `END` всем подключённым садовникам и наблюдателям. События и итог также записываются в `simulation.log`.

## 3. Сборка и запуск

Для сборки нужен компилятор C11 и `make`. Для автоматических проверок нужен Python 3.

```sh
make
```

При необходимости на macOS можно указать SDK явно:

```sh
SDKROOT=/Library/Developer/CommandLineTools/SDKs/MacOSX26.5.sdk make
```

Каждая команда запускается в отдельном терминале из каталога проекта:

```sh
./garden_app 127.0.0.1 9000 --defaults
./gardener_app 127.0.0.1 9000 101 15
./gardener_app 127.0.0.1 9000 102 20
./monitor_app 127.0.0.1 9000
./monitor_app 127.0.0.1 9000
```

После подключения клиентов нужно нажать Enter в терминале сервера. Для проверки переподключения во время полива один наблюдатель закрывается через Ctrl+C и запускается той же командой. Второй наблюдатель продолжает получать события. Для запуска по сети сервер привязывается к своему сетевому IPv4-адресу или к `0.0.0.0`, а клиенты указывают IPv4-адрес сервера и его порт.

При запуске без `--defaults` сервер запрашивает параметры в таком порядке:

| Параметр | Значение по умолчанию |
|---|---:|
| Количество цветов | 8 |
| Начальная влажность | 80 |
| Минимальная скорость высыхания | 1 |
| Максимальная скорость высыхания | 3 |
| Порог увядания | 40 |
| Порог засыхания | 15 |
| Объём полива | 30 |
| Интервал защиты, с | 10 |
| Длительность симуляции, с | 60 |
| Шаг симуляции, мс | 100 |

Enter оставляет значение по умолчанию. Шаг времени должен быть от 1 до 60 000 мс. Длительность `0` или меньше снимает ограничение по времени. Начальное состояние задаётся флагом `--initial-state` (`auto`, `normal`, `watered`, `wilting`, `dried`, `overwater`). В режиме `auto` оно определяется влажностью и порогами. При состоянии `watered` защита действует с начала симуляции. Если ID садовника пропущен или равен `0`, сервер назначает его сам. Скорость садовника по умолчанию — 15.

Для короткого показа можно задать параметры через стандартный ввод. В этом случае сначала подключаются наблюдатели, затем садовники. Сервер стартует после регистрации второго садовника. Флаг `--seed` задаёт начальное значение генератора случайных скоростей.

```sh
printf '%s\n' 3 48 4 5 40 15 25 6 30 100 |
  ./garden_app 127.0.0.1 9000 --gardeners 2 --seed 13
```

## 4. Результаты проверки

Проверки выполнены на macOS через TCP на адресе `127.0.0.1`. Автоматические сценарии из `tests/integration.py` запускаются командой `make test`. Команда `make test-local` прогоняет те же сценарии через локальные потоковые сокеты.

| Сценарий                                                                              | Результат                                                                                                                                                        |
| ------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Два наблюдателя, один из них переподключается во время полива.                        | Вернувшийся наблюдатель получил снимок работающей клумбы. Дальнейшие события и итоговая строка совпали у обоих наблюдателей.                                     |
| Два садовника выбрали один цветок.                                                    | Первый обработанный запрос начал полив. Второй получил `RETRY`.                                                                                                  |
| Садовник повторил запрос во время защиты.                                             | Устаревший запрос получил `RETRY`. Запрос с актуальным числом поливов дал `OVERWATER`, после гибели последнего цветка сервер завершился с `END reason=all_dead`. |
| Садовник отключился во время полива и вернулся с тем же ID.                           | Сервер отменил незавершённый полив. После переподключения садовник получил цветок и завершил полив.                                                              |
| Команда регистрации отправлена в два приёма, отдельно отправлена неизвестная команда. | Сервер собрал корректную команду и выдал снимок. На неизвестную команду ответил `ERROR`.                                                                         |
| Один цветок, без садовников и лимита времени.                                         | После засыхания цветка сервер выдал `END reason=all_dried`.                                                                                                      |
| Ctrl+C на сервере до начала симуляции.                                                | Ожидающий садовник и наблюдатель получили `END reason=signal` и завершились.                                                                                     |

Вывод при переподключении наблюдателя:

```text
SNAPSHOT phase=running time=0.100 flowers=3 alive=3 gardeners=2
EVENT [t=0.900] WATER_DONE gardener=102 flower=1 moisture=56.000 protected_until=1.200
END reason=duration time=2.400 alive=3 total=3 normal=2 watered=0 wilting=1 dried=0 overwater=0 cycles=3
```

Отдельно проверены два граничных случая. В первом начальное состояние — `watered`, начальная влажность — 41, порог увядания — 40, скорость высыхания — 2, интервал защиты — 2 с. Садовник был готов с начала прогона. Цветок увял на 0,5 с, а полив начался в момент окончания защиты на 2,0 с:

```text
EVENT [t=0.500] STATE flower=0 WATERED -> WILTING moisture=40.000
EVENT [t=2.000] WATER_START gardener=7 flower=0 moisture=37.000 speed=20
EVENT [t=2.200] WATER_DONE gardener=7 flower=0 moisture=41.000 protected_until=4.200
```

Во втором случае в качестве шага времени введён `0`. Сервер вывел `Некорректное значение: Шаг времени в миллисекундах` и завершился с кодом `1` до открытия порта.

## 5. Использование ИИ

Искусственный интеллект использовался для разбора TCP по материалам семинара, доработки кода и проверки граничных случаев. При проверке отдельно разобраны ожидание полива после окончания защиты цветка и обработка нулевого шага симуляции. Результаты этих прогонов приведены в разделе 4. Также ИИ помог привести отчет в более читаемый вид.

Запросы отправленные ИИ:
